### 1.1 must-fix | confidence high | reproduced | untouched by 2945344/cfad0aa/826d58a
File: src/rsicontext/participant/snapshot.py:333 (`return dict(snapshot.memory)`),
:406-409 (`LearningCarry(memory=dict(snapshot.memory), ...)`); contract at :25-27.
Defect: dict() is a SHALLOW copy — nested containers inside snapshot.memory stay shared by
reference between the live snapshot, the LearningCarry, and every branch session.
@dataclass(frozen=True) stops attribute rebinding only; it does not freeze the payload.
Scenario (reproduced): a hook uses the natural in-place form
`self.state["nested"]["keep"] = 999` or `self.state.setdefault("notes", []).append(...)`,
the exact shape of _ScriptedHook at tests/test_snapshot.py:93-94 (that test passes only
because it REBINDS "notes" via setdefault). Result: snapshot.memory becomes
{'nested': {'keep': 999}, 'notes': ['kept from dev', 'branch-A note' x6]};
canonical_bytes() != before; a SECOND branch run starts with branch 1's notes —
cross-branch read leak plus snapshot write-back, the two things the module exists to
prevent. Secondary: FrozenSnapshot is eq=True hence value-hashable, so its hash changes
while stored as a dict key. Contradicts snapshot.py:25-27 and
docs/snapshot-carry-20260921.md:54 ("bit-identical before/after"), the acceptance case
that doc claims is tested.
Fix: copy.deepcopy at the three boundaries, or store memory as canonical bytes and
json.loads a fresh copy per branch.
CLEAN: parent dev store unreachable — branch save_state writes only through the
branch-local SessionStateStore (store.py:259-279, session-namespaced).

### 2.1R should-fix | confidence high | reproduced | OPEN at 2945344, cfad0aa, 826d58a
File: src/rsicontext/lifecycle/runner.py:304-323 (_commit_gate_failures; unchanged through
826d58a).
Defect: `referenced` is built ONLY from the commit record's "provenance", and the domain
requirement fires only `if domain_record is not None` (:318-322). A commit with no
references skips BOTH the domain check and the revision-currency check; only plan-membership
survives.
Scenario (reproduced at 2945344):
  (a) `create_record` only — no finalize at all — plan=aurora, status="final" ->
      final check PASSED with zero verification_run and zero candidate_status records;
  (b) plain finalize with provenance=("doc-cand-a",) and no referenced records -> PASSED
      (the participant supplies a payload-derived provenance entry and disables the
      remaining checks).
At cfad0aa this propagates: reproduced on BOTH new worlds — orinoco (kestrel) and
parana (basalt): "create-only, legal plan name, status final, NO verifications -> True ()"
and "plain finalize, no refs, no verifications -> True ()".
Untested because every gate test supplies a domain-bearing reference:
tests/test_commit_gate.py:35-77 and tests/test_worlds_v3.py:56-67 both always emit and ref
candidate_status-{plan}. The hole is exactly those hooks minus one record.
This is the same "necessary-history condition" docs/task-card-research-v3.md:112-120
promises.
Fix: when plan_requirements names the committed plan, require a non-empty referenced set
(and a candidate_status record for that plan) instead of skipping on absence — absence is
evidence FOR the failure, not neutral.

## VERDICT

The v3 work is honest and the three follow-up commits are real improvements — 2945344
genuinely closes the plan-legality bypass, and 826d58a turns the trajectory's new-world
branch into an actual transfer test over unseen material (ran it: fixed and S0 fail the
evaluator gate on both surfaces, S1 passes; the contrast is preserved and now measured on
the check surface rather than an incidental exception). But the two most consequential
problems found are still open. 2.1R leaves the same "necessary-history condition" the task
card promises bypassable: a participant that references nothing — or that emits a bare
create_record with status "final" and never finalizes — passes with zero verification
records, and this now holds on all three worlds (main, orinoco, parana), so the variant pool
inherits it. 1.1 is worse in kind, not degree: the "byte-frozen" snapshot is not frozen
against in-place mutation of nested carried values, and one branch's writes reach its
siblings, which falsifies the isolation guarantee the module was written to provide — and
because it reproduces with ordinary in-place participant code, it is the failure mode most
likely to appear silently in a real run. Then 2.2 (a crashing researcher edit still reports
as "the improvement did not transfer"), then 1.2/1.3/4.1 and the 6.x gaps. Suggested order:
2.1R, 1.1, 2.2, then the rest. Each fix is a small, targeted diff at the cited lines — none
requires re-architecting what has been built.
