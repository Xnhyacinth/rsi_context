# Findings

- Pack-8K is a historical HELMET instrument, not the open-S evolution envelope.
  Full-as-fits long context is a legal strategy; the live cell uses the frozen
  reader window (hy3 pack 114624 after a 128960 overflow). Items longer than the
  window still need fit.
- The 8K dual-role campaign did not self-evolve: round 0 was a byte-identical
  H0 hold invited by "preserve files unless changing"; round 1 exited 1 before
  a scorable tree. Identical parent copies are now invalid; object payloads merge.
- On 16 unseen PopQA k1000 items, frozen open-S H0 (query overlap) scored 0.500
  versus head 0.3125 and head-tail 0.375; the handwritten BM25+2hop hybrid scored
  0.625 with the same 0.4375 gold-chunk recall as H0. Overlap retrieve is not
  BM25. Head truncation packed zero gold chunks. This is a one-pass hy3 landscape,
  not researcher advantage.
- LongMemEval-V2 small 8K packs, zero reader: on the 294 deterministic items,
  answer-string presence was last-k 0.112, lexical 0.408, random 0.361. All 128
  weak-judge items were 0. This is coverage of the answer string, not official
  accuracy, and not a researcher loop.

- Open-S is harness evolution of a folder strategy system S under a frozen
  reader, not a new Recuris-style method claim. Borrow archive/clone isolation
  and rewritable retrieve/route/memory files; do not leak gate scores, uncounted
  evals, extra reader calls, or internet tools. Report it separately from
  PolicySpecV1 A2. An open folder is not researcher advantage until it beats
  matched sampling and sequential refinement (2607.12227).
- Recuris removes any defensible novelty claim around first external
  context/memory evolution or first frozen-model long-horizon improvement. The
  remaining D&B gap is a multi-researcher, matched-search, replay-calibrated,
  predict-before-evaluation benchmark of context-policy research.
- Static long documents and live long-horizon tasks are complementary, not
  substitutes. Static one-call evaluation is the primary identification layer;
  offline trajectories and one final retry-matched live task test external
  validity after a policy is frozen.
- PostTrainBench's 10-hour H100 budget and RSIBench-Data's 16-hour/$500 budget

  researcher discovery.

# 2026-08-29 — Recuris-aligned study design findings

## What transfers cleanly

- Recuris makes the invariant machine and the evolving artifact explicit. The
  RSIBench-Context analogue remains: frozen reader/evaluator versus editable
  context policy. This supports the existing three-way boundary; it does not
  justify widening the editable surface.
- Its acceptance gate is arithmetic rather than generative: paired held-out
  evidence plus a regression cap. For this project, paired item-level
  bootstrap and anchor-regression diagnostics are appropriate, but hidden gate
  outcomes must remain one-shot and evaluator-only. They cannot become
  round-by-round researcher feedback without changing the estimand.
- Its mechanism fingerprint is a useful missing audit. The context-policy
  analogue should record whether a candidate actually changed selected spans,
  allocation, ordering, verification, or abstention on the items it claimed to
  target. This is evaluator-owned attribution evidence, not a search fitness.
- Its component-scoped patch and prediction manifest maps naturally to this
  project's manifest calibration: each round should name the changed policy
  components, predicted item flips/regressions, and expected cost direction.
- Its file-based cross-round state and structured sanitized feedback are
  compatible with a coding-researcher benchmark. The benchmark driver, not a
  hidden conversational context, must define what persists between rounds.
- Bootstrap resampling units must be independent items or trajectories, never
  repeated replays of the same item. Replays estimate the noise floor only.

## What must not be copied into the primary study

- Recuris evolves working memory, checkers, and task plugins. Adding these to
  static A2 would enlarge the genotype beyond the preregistered context policy
  and turn the benchmark into a different method paper. They belong, if used,
  only in the separately labelled long-horizon transfer arm.
- Recuris's progressive hidden admission gate conflicts with the primary
  visible-selection/one-shot-isolated-gate design. Borrow the statistical
  checks, not the feedback channel.
- Human-reviewed task plugins, oracle knowledge, model judges, retries, and
  simulator-specific settings are not matched static-policy baselines. They
  require separate accounting and claims.
- Its four rounds, k=4, regression cap of one, and simulation budget are
  application-specific values, not defaults for this project.

## Current scientific bottleneck

- The protocol and A2 resource envelope are substantially specified, but the
  second real causal multi-hop profile is not frozen and has no qualified
  pinned adapter. Existing HELMET/PopQA assets are useful for real
  long-document routing, while the current Hotpot-derived path is not yet an
  adequate causal multi-hop profile because some records are non-extractive
  and the present lexical setting can saturate.
- The next valid action is an offline qualification comparison for one
  supporting-fact dataset family (MuSiQue, HotpotQA distractor, or 2Wiki), then
  registry review and a small reader qualification. Running researcher loops
  before this gate would measure optimization on an under-specified task.
- KV/HBM/prefix-cache/scheduler optimization is not part of the primary
  semantic-policy estimand. Those signals may be reported only when an
  attested local serving stack exposes them, and any KV policy remains a
  separate track.

# 2026-08-29 — provider implementation audit constraints

- The requested local-vLLM and Tencent paths are both expected to use an
  OpenAI-compatible HTTP transport. The implementation should reuse one reader
  contract and vary only a frozen provider profile; separate evaluation paths
  would introduce avoidable drift.
- Secrets in shell initialization are out of scope for inspection and artifact
  capture. Configuration may name an environment variable, but tests, plans,
  logs, manifests, and error messages must never contain its value.
- A remote alias such as `hy3-ioa` can be used immediately for qualification and
  researcher debugging. Formal reader use requires response-model identity,
  usage accounting, deterministic replay/drift checks, and explicit marking of
  API-unobservable GPU/HBM/KV/cache/scheduler fields.
- The next design decision depends on the existing `openai_compatible`, API
  profile, registry-serving, and canary implementations; no new SDK or provider
  abstraction is justified until those files are read completely.

## Initial implementation evidence

- The repository already has the correct core shape: a standard-library,
  fail-closed `OpenAICompatibleReader`, strict API profiles, a repeated Tencent
  canary, registry-pinned vLLM serving profiles, and hold-wrapped dry-run command
  generation. Adding an OpenAI SDK or a second reader class would be redundant.
- The reader already blocks redirects/proxies, host drift, insecure remote HTTP,
  embedded credentials, missing token usage, response-model mismatch, output
  overrun, and model-length overrun. It accepts a secret only as a non-repr,
  non-comparable field.
- Existing Tencent tests already target `hy3-ioa`, streaming SSE with usage,
  response-model identity, stable answers/usage, secret non-persistence, and an
  unversioned-provider flag. The likely missing work is safe environment
  resolution, a shared provider-to-reader construction/preflight path, and
  runtime attestation—not another transport implementation.
- Local serving command generation already emits the required
  `/workspace/wynckeliao/ops/gpu/hold.sh wrap ... vllm serve` shape and freezes
  context length, TP/DP, dtype, prefix cache, chunked prefill, seed, and Qwen
  reasoning flags through a hashed serving profile.

## Concrete gaps after reading the core files

- `APIProfile` already represents both local and remote providers, but
  `api_key_env` is mandatory and `scripts/api_canary.py` requires a non-empty
  key. A default vLLM server commonly has no key, so local qualification is
  artificially blocked or encouraged to use a dummy secret.
- `run_api_canary` rebuilds `OpenAICompatibleReader` directly. Other scripts also
  construct the reader directly, which risks profile drift and makes safe
  environment handling inconsistent. A single small profile-to-reader factory
  is warranted; a new transport class is not.
- `OpenAICompatibleReader.from_run_spec` is intentionally a pinned local-serving
  constructor: it requires a registry model, `ServingProfile`, and exact model
  revision. It should remain strict. A remote unversioned provider needs a
  separate labelled qualification constructor rather than weakening this
  formal local binding.
- `APICanaryResult` records the endpoint URL. The endpoint validator forbids
  query strings and embedded credentials, so this is not currently a secret,
  but the planned runtime artifact should still store normalized endpoint
  identity and observability flags rather than headers or environment values.
- The local profile model string (`Qwen/Qwen3.6-27B`) correctly matches the
  served Hugging Face identifier, while the registry/serving profile uses the
  internal id (`qwen3.6-27b`). These are deliberately joined by
  `validate_run_binding`; they should not be collapsed into one ambiguous id.

## Script duplication and intended minimal seam

- `autonomous_dynamic_pilot.py` and `autonomous_public_pilot.py` duplicate the
  same local-versus-remote branch, environment lookup, reader construction, and
  `DynamicReaderIdentity` assembly. This is the highest-value consolidation:
  it affects real runs and currently permits options such as timeout/output cap
  to drift between scripts.
- The consolidation should live next to `APIProfile`, because both local vLLM
  and Tencent resolve to that frozen profile before evaluation. Dataset loading,
  researcher launching, and evaluation stay in their current modules.
- The local path currently bypasses environment resolution by taking an
  explicit loopback endpoint and no key. The generic canary path cannot do the
  same. The profile schema needs an explicit optional-key contract or an equally
  explicit resolver rule; silently substituting a dummy key is unacceptable.
- The worktree already contains earlier project changes. New edits must be
  limited to provider/runtime helpers, the scripts that duplicate them, focused
  tests, documentation, and planning records; unrelated modified files remain
  untouched.

## Chosen implementation boundary

- Keep `OpenAICompatibleReader` unchanged as the single transport and keep its
  strict `from_run_spec` path for formal pinned local runs.
- Extend `APIProfile` with an explicit `api_key_required` flag. Tencent remains
  key-required; local vLLM profiles set it false. This is safer and more
  reproducible than detecting localhost heuristically or accepting dummy keys.
- Add one environment/override resolver and one profile-to-reader factory in
  `experiment/api.py`. These helpers can serve the canary and visible
  qualification scripts without creating a provider class hierarchy.
- Extend canary evidence with fixed observable and unobservable field names so
  API runs state exactly what they can establish. Do not infer GPU/HBM/KV/cache
  or scheduler state from HTTP responses.
- Consolidate the duplicated local/remote reader preparation in the two
  autonomous scripts only after the helper tests pass. Campaign data and policy
  logic are not part of this refactor.

## Repository conventions affecting the change

- Public experiment helpers are re-exported through
  `rsicontext.experiment.__init__`; new runtime helpers need explicit exports and
  strict mypy coverage.
- The package deliberately has zero core dependencies and uses `urllib`; the
  provider work must preserve that dependency boundary.
- `runtime_attestation.py` already exists and should be composed with rather
  than replaced by API canary evidence. The canary proves protocol/identity/
  replay behavior; formal attestation proves process and frozen artifact
  identity where observable.
- Existing README and `docs/api-hy3-experiment-plan.md` already document the
  remote replication boundary. The new runbook should update those paths rather
  than add a competing provider document.

## Adapter source decision after pinned-repository inspection

- MuSiQue official format directly exposes paragraph `idx`, `title`,

- 2Wiki adds evidence triples and more reasoning types, but its corrected archive

  valuable later after provenance is repaired.

  real reader qualification stays blocked until the archive checksum and

## MuSiQue adapter boundary

- The existing `EvaluationItem` is evaluator-facing: it contains the answer and
  gold chunk IDs. A MuSiQue parser should not invent a second evaluation loop;
  it should compile into that representation and retain decomposition metadata
  only in an evaluator-owned wrapper.
- Gold provenance must come from explicit `is_supporting`/decomposition fields,
  never from answer substring matching. This lets answer deletion, gold drop,
  and sufficiency tests target the stated evidence rather than accidental
  mentions in distractors.
- The first adapter should require the answerable split, validate unique and
  complete paragraph/support indices, and preserve source order. Long-context
  distractor expansion is a later frozen transform; mixing it into the parser
  would make source validation and position interventions harder to audit.

## 2026-08-29 release-builder design decision

- The repository has no existing HF release builder. The smallest safe design
  is a deterministic, standard-library-only allowlist builder: a tracked JSON
  specification names each permitted source file and its license/provenance;
  the builder copies only those files and emits a dataset card plus SHA-256
  manifest into ignored `artifacts/` staging.
- The initial HF payload will contain only the project-authored synthetic
  MuSiQue fixture. It will explicitly exclude official datasets, LongMemEval
  screenshot archives, raw API responses, results, and gate/sealed material.
- The release tests must prove deterministic output, exact allowlisting,
  digest correctness, refusal of dirty/unsafe paths, and a 40-character source
  revision. No new dependency is required.

### Independent review correction

- A SHA-shaped `source_revision` is insufficient provenance. The safe builder
  must prove that the revision exists, equals the repository's current `HEAD`,
  and that the entire non-ignored worktree is clean before staging. Otherwise a
  dirty fixture or builder could be uploaded under an unrelated commit.
- Payload bytes must be captured once and those same bytes written and hashed;
  a second filesystem read permits a time-of-check/time-of-use mismatch.
- All entries must validate before any publishable output exists, and staging
  must be atomically renamed into place so a failed build cannot leave a
  partial upload directory.
- The diagnostic artifacts retain endpoint metadata but no credentials. The
  11-call diagnostic was bounded during this session, not preregistered in a
  prior immutable record; the public note must use those exact terms.

## 2026-08-29 `hy3-ioa` dual-role adapter audit

- The campaign boundary is reusable: `run_researcher_campaign` materializes a
  clean parent policy workspace, requires only `policy/` plus `manifest.json`,
  audits every Python file, validates prediction coverage and parent lineage,
  evaluates a byte snapshot in a fresh process, and records invalid researcher
  turns without spending reader calls.
- Existing researcher adapters assume a file-editing Codex/Claude CLI. A plain
  chat-completions model has no filesystem tools, so the smallest safe addition
  is a stateless API worker that requests one strict JSON artifact containing
  `policy_source` and `manifest`, validates both, and writes only the two
  allowed submission paths in the ephemeral campaign workspace.
- Reusing the reader profile unchanged is insufficient: its 512-token output
  cap cannot hold a policy plus manifest and its system prompt is answer-only.
  Add a separate researcher API profile with the same endpoint/model alias but
  its own output cap and profile hash. Record the researcher system-prompt hash
  and every round-prompt hash independently from the reader identity.
- The secure HTTP/SSE implementation can be shared without merging roles. Add a
  generic `complete(user_prompt)` path to the OpenAI-compatible transport while
  leaving evaluator `read(query, ContextPack)` and its default system prompt
  unchanged. The campaign still owns all scored reader calls.
- The first experiment must be adapter/schema qualification, not A2: at most
  three researcher calls, then a two-round visible toy/dynamic loop. Only a
  valid audited submission and complete usage/identity record can promote to
  the 2-profile × 2-seed × 5-slot long-context block.
